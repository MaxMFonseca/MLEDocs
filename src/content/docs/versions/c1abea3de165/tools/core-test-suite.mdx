The automated surface consists of two GoogleTest executables: `Core` and the separate `AudioLifecycle` shutdown suite. CMake discovers both with the `unit` label. The pinned tree contains **29 `T.*.cpp` translation units**; the interactive `Client` executable is not one of them.

## Build and run

With `MLE_BUILD_TESTS=ON`, configure and build as described in [Run the automated tests](../../start-here/tests/). From a repository-root shell that has sourced `scripts/envsetup.sh`, the helper prepares the Core resource tree and forwards GoogleTest arguments:

```bash
mle_run_test -n Core -t Debug
mle_run_test -n Core -t Debug -- --gtest_filter=ThreadPoolTest.*
```

Use the actual suite and test names printed by `--gtest_list_tests` when composing a filter. `AudioLifecycle` is emitted at `build/<build_type>/tests/Core/AudioLifecycle`; the helper's name-to-directory convention cannot launch it, so run that executable directly. The inspected first-party CMake does not establish a verified root `ctest` entry point.

## Runtime and resource boundary

`Core` initializes Core, Client, and Renderer, calls `RUN_ALL_TESTS()`, then shuts down Renderer and Core. It does not explicitly shut down Client or Window. `AudioLifecycle` stays separate so shutdown tests can control the audio mailbox and final-drain thread without the main runner's lifecycle.

The helper rebuilds `build/<type>/tests/Core/res`, linking engine resources under `mle` and `tests/Core/res` under `i`. Those test resources include Lua modules, shaders, and textures. Suppressed link errors and the helper's final status are not proof of a passing run; use GoogleTest's result and logs.
