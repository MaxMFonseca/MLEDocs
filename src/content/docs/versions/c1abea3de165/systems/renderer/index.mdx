MLE's renderer is a set of Vulkan services owned by the `Renderer` singleton. `Renderer::init()` creates the Vulkan context, command and synchronization managers, frame renderer, then the shader, pipeline, texture, font, mesh, skeleton, and animation caches. `shutdown()` waits for the device before releasing those owners in reverse dependency order. See [`Renderer.cpp`](https://github.com/MaxMFonseca/MLE/blob/c1abea3de165032fe064300340807b7a6af388f8/src/mle/renderer/Renderer.cpp).

## Choose the owner page

- [Frame, Vulkan, and queues](./frame-vulkan-and-queues/) owns device requirements, frame slots, acquire/submit/present, and command-thread rules.
- [Resources and synchronization](./resources-and-synchronization/) owns buffers, images, transfers, layouts, cache readiness, and deferred deletion.
- [Shaders and pipelines](./shaders-and-pipelines/) owns compiled shader discovery, SPIR-V reflection, descriptors, push constants, and graphics/compute state.
- [Targets, text, and composition](./targets-text-and-composition/) owns dynamic-rendering attachments, image composition, textures, atlases, and fonts.
- [Models](../models/) owns GLTF, meshes, materials, skeletons, animations, and cameras.

## Lifecycle boundary

Call `Renderer::stop()` before `shutdown()` so the frame jthread is requested to stop and joined. Vulkan-backed resources must be destroyed while their device and owning cache remain alive. `Renderer::shutdown()` does wait for device idle, but the wider application entry path is still in development; do not treat scope exit as a documented automatic shutdown sequence.

## Prerequisites and maturity

The client renderer requests Vulkan 1.3, swapchain and push-descriptor extensions, synchronization2, dynamic rendering, descriptor-indexing features, buffer device addresses, and several dynamic/raster features. The selected device, queues, formats, and present mode remain platform-dependent. The current device creation code does not comprehensively preflight every requested feature.

## Test evidence

The Core renderer suite checks representative behavior rather than the entire runtime loop:

- [`T.FrameRenderer.cpp`](https://github.com/MaxMFonseca/MLE/blob/c1abea3de165032fe064300340807b7a6af388f8/tests/Core/src/renderer/T.FrameRenderer.cpp) verifies the preferred sRGB swapchain surface format.
- [`T.Buffer.cpp`](https://github.com/MaxMFonseca/MLE/blob/c1abea3de165032fe064300340807b7a6af388f8/tests/Core/src/renderer/T.Buffer.cpp) covers creation, mapping, staging, copies, and persistent writes.
- [`T.Image.cpp`](https://github.com/MaxMFonseca/MLE/blob/c1abea3de165032fe064300340807b7a6af388f8/tests/Core/src/renderer/T.Image.cpp) covers image creation and views, uploads, copies, blits, file loading, and PNG saving.
- [`T.Pipeline.cpp`](https://github.com/MaxMFonseca/MLE/blob/c1abea3de165032fe064300340807b7a6af388f8/tests/Core/src/renderer/T.Pipeline.cpp) and [`T.Shader.cpp`](https://github.com/MaxMFonseca/MLE/blob/c1abea3de165032fe064300340807b7a6af388f8/tests/Core/src/renderer/T.Shader.cpp) exercise graphics and compute pipeline creation plus SPIR-V reflection data.

These tests support the listed behaviors. They do not establish API stability, cover the complete frame loop, or prove every platform and presentation path. Model Test behavior is a shipped demonstration rather than a guarantee.
